# DDLL-Agent-UI/UX

面向 AI 设计协作的中文 UI/UX 技能，将需求核对、Figma 设计执行、组件与变量复用、视觉检查和需求验收组织为可连续推进的工作流程。

它适合在已有产品、组件库和设计规范中处理真实设计任务：先查清业务变化和来源，再复用完整旧结构，在授权范围内修改，最后用内容对账、结构读回和实际渲染验证结果。

本仓库以设计工作流和规则为主。技能入口是 [SKILL.md](SKILL.md)，本说明用于帮助使用者理解能力、准备资料和发起任务；实际执行以技能主文件、本轮适用引用及用户有效要求为依据。

## 适用场景

| 场景 | 主要工作 | 关键边界 |
|---|---|---|
| 新需求设计 | 完整读取需求和原型，拆出实际设计变化，准备副本并按功能出稿 | 不把每条业务规则都扩成新页面，不补画无依据状态 |
| 旧稿增量修改 | 定位适用端、版本、语言和现行稿，在完整旧结构上做最小修改 | 保留未涉及的导航、字段、样式、数据和组件关系 |
| UI 组件与组件库 | 追溯真实母组件、嵌套组件、属性、变体和 Slots，修改授权能力 | 不打散组件，不用叠层或散帧冒充复合组件复用 |
| 表格与报表 | 核实列、分组、行粒度、汇总、筛选、完整分页及宽表结构 | 不为适配删列，不凭示例值推断统计口径 |
| 还原与迁移 | 对照指定来源迁移必要结构和依赖，核对目标已有内容 | 不凭名称判断等价，不覆盖已有能力或独有内容 |
| 视觉与结构评审 | 核对渲染、布局、文字、颜色、变量、组件关联及完整边界 | 纯评审只读，发现问题不自动获得修改授权 |
| 与线上或现行界面对齐 | 区分实际观察、组件能力、已有说明和运行验证 | 静态外观一致不等于交互已实现 |
| 配色、图标、插画与新风格 | 在授权方向和适用来源内组织视觉语言 | 个人品味不覆盖指定旧稿与组件库规范 |
| Figma 动效 | 在任务明确涉及动效时使用原生 Motion 时间轴和关键帧 | 静态截图不能证明动效已播放或真实业务能力已实现 |
| 规则收录 | 将用户明确希望长期保留的习惯合并到合适位置 | 不将项目资料、节点 ID、一次性测量或故障流水写成通用规则 |

## 安装与调用

### 1. 安装完整技能目录

依据 [OpenAI 官方技能文档](https://developers.openai.com/codex/skills/)，Codex 支持用户级 `~/.agents/skills` 和仓库级 `.agents/skills`，也支持指向技能目录的软链接。以下以用户级手动安装为例：

```bash
mkdir -p ~/.agents/skills
git clone https://github.com/Yomi-Five/ddll-agent-ui-ux.git \
  ~/.agents/skills/ddll-agent-ui-ux
```

访问私有仓库时，需要当前 GitHub 账号已有相应读取权限。目录已存在时先核对其来源，不覆盖现有文件，也不重复安装同名技能。

如果只希望当前项目使用，将完整仓库放在该项目的 `.agents/skills/ddll-agent-ui-ux` 下。已有其他有效技能目录或软链接的环境可继续使用原有安装方式，本说明不要求迁移现有配置。

必须保留 `SKILL.md`、`agents/`、`references/`、`taste.md` 和 `inbox.md` 的相对位置。只复制主文件会丢失按场景加载的细则。

对于通过 `git clone` 安装、且没有需要保留的本地修改的副本，可在确认工作区状态后更新：

```bash
git -C ~/.agents/skills/ddll-agent-ui-ux status --short
git -C ~/.agents/skills/ddll-agent-ui-ux pull --ff-only
```

### 2. 显式调用

在支持 `$` 技能提及的 Codex 环境中，可以这样发起任务：

```text
$ddll-agent-ui-ux
请依据我提供的需求文档和原型，完成指定端的设计修改。
先核对现行稿和组件库，在完整旧结构副本中做本次明确变化，完成后验收。
```

其他界面通过其技能选择器选择 `DDLL-Agent-UI/UX`；具体入口以所用客户端为准。

### 3. 按任务自动匹配

当前配置未关闭隐式调用，宿主可根据技能描述和任务语义选择它。匹配依据涉及设计、Figma、UI、组件库、排版、配色、动效、图标、插画及设计评审；并非出现某个词就保证触发。

技能采用渐进加载：先暴露名称与描述，被选中后读取 `SKILL.md`，再按任务读取相关引用。正常设计任务不需要每次通读全部参考文件。

Codex 会检测技能变化；若更新未出现，可重启后检查技能列表。不要以“文件已放入目录”代替实际可发现、可调用的确认。

## 工具与资料准备

技能提供工作方法，实际执行依赖当前环境可用的工具、账号权限和来源资料。它不附带 Figma 连接服务、账号凭据或可直接套用的组件库文件，也不会仅因安装就取得文件编辑或发布权限。

| 任务 | 需要的条件 | 条件不足时如何处理 |
|---|---|---|
| 阅读本地需求、规则或设计说明 | 可访问的资料或本地文件 | 标明缺失资料和影响范围，不用摘要补猜正文 |
| 阅读飞书需求及 HTML 原型 | 适用飞书工具、文档与附件读取权限 | 分别定位正文、附件、权限或资源类型问题 |
| 读取 Figma 结构、查库或受支持复制 | 当前 MCP 或其他适用工具具备相应能力 | 核实实际接口，不假定旧工具调用仍然可用 |
| 编辑设计、改字和本机渲染验收 | 已确认目标的 Console MCP／Desktop Bridge 连接及编辑权限 | 暂停依赖连接的编辑和本机验收，继续可独立的资料工作 |
| 跨文件保真复制 | 当前受支持的文件复制能力；必要时使用已有授权的原生界面路径 | 保留母组件、嵌套、变量与样式关联，不用无关联副本替代 |
| 独立子 agent 检查 | 宿主提供协作能力及足够并发条件 | 由主 agent 按职责顺序检查，如实说明未做独立复核 |
| 发布库并验证业务实例 | 用户完成发布，且可读取消费者实际版本 | 分别报告母组件修改、发布、实例更新与本机验证状态 |

发起任务时，尽量提供需求入口、原型入口、适用端／版本／语言、现行稿或目标文件，以及需要保留的内容。组件来源、尺寸和节点关系由执行者在可访问资料中核实，不要求用户手工整理所有可查询事实。

## 如何描述任务

以下是任务表达示例，用于说明如何给出边界，不会作为组件文案、默认数据或新业务规则写入设计。

### 新需求或旧稿增量

```text
使用 ddll-agent-ui-ux 处理这份需求：〔需求入口〕。
原型：〔原型入口〕；现行稿：〔Figma 入口〕。
本次只做〔指定端／版本／语言〕的〔实际变化〕。
保留现行稿中未涉及的导航、字段、文案和组件关系，按完整功能连续完成并验收。
```

### 表格恢复或修改

```text
使用 ddll-agent-ui-ux 恢复〔目标表格／页面〕。
依据〔完整来源〕核对列顺序、分组、合并关系、数据与汇总口径，
同时恢复范围内的筛选、操作区和完整分页，保留原有页面框架。
```

### 组件能力修改

```text
使用 ddll-agent-ui-ux 修改〔组件入口〕的〔明确能力〕。
请先确认真实母组件、嵌套和使用范围，仅修改指定能力并检查相关变体与业务实例。
保留其他属性、Slots、变量和默认表现；库发布由我处理。
```

### 只读评审

```text
使用 ddll-agent-ui-ux 只读检查〔Figma 入口〕。
对照〔需求／原型／现行稿入口〕，报告内容、视觉、结构和组件关联差异。
给出具体位置、依据和影响，不修改设计。
```

### 续做

```text
继续当前设计任务，沿用最新任务记录、有效来源和已确认例外。
先核实上次实际完成状态，只补未完成项，不重复建文件或复制稿件。
```

### 收录通用习惯

```text
将这条习惯收录到 ddll-agent-ui-ux：〔规则〕。
适用条件为〔条件〕，例外为〔例外〕，验收时检查〔可观察结果〕。
请与现有对应规则合并，去掉项目名称、单次参数和操作过程。
```

## 来源分工与修改边界

技能不使用一个总排名让某类资料覆盖所有维度，而是核实每类来源负责什么：

| 来源 | 负责的维度 |
|---|---|
| 用户最新有效要求 | 本轮范围、授权、修正和明确例外 |
| 完整需求文档 | 业务变化、字段含义、条件和验收要求 |
| 指定原型 | 流程、入口、字段和交互意图 |
| 指定现行稿 | 未改内容、页面框架、实例实际表现和视觉基准 |
| 实际所属组件库 | 可复用结构、属性、Slots、状态、变量和主题能力 |
| 通用规则与个人品味 | 填补上述来源尚未明确规定的部分 |

原型中的简写、占位、示意样式和省略，不自动构成修改通用字段、删除现行内容或更换页面框架的依据。确有新增或修改的业务项仍需落实，不能以“旧稿没有”漏掉。

开始修改前，对当前受影响对象明确：**对应来源、允许变化的属性、必须保留的内容、执行动作和验收方法**。发生真实冲突时查原始资料；仍不能解决的仅暂停依赖部分，不以猜测继续，也不阻塞独立工作。

## 核心设计规则

### 1. 出稿范围和状态必须有依据

当前技能包含用户明确的长期限制：**无双需求不出设计稿**。混合需求中可读取无双内容理解业务依赖，但不得据此创建或补画无双页面、弹窗、状态及专用组件。只有用户明确撤销或变更该限制时才调整。

页面、弹窗、入口及状态组合，必须在适用旧稿、指定原型中有依据，或获得用户明确新增指示。不能因“完整覆盖”“补齐边界场景”而自行扩画错误、权限、空状态或其他状态。

这些是当前技能的执行边界。使用者接入其他工作环境时，应先了解并明确处理这些约束，而不是将其当成所有产品的通用规则。

### 2. 让布局解释

最高视觉原则是：通过分组、对齐、间距、层级和位置表达信息，减少不必要的辅助标签、副标题、解释段落及重复说明。

必要的字段名、操作、业务限制和错误提示仍需保留。不能用新增文案补救布局，也不能以简洁为由删除必要信息。

### 3. 复用完整旧结构并保护文案

存在适用旧稿时，先复制或复用完整结构，再落实本次明确变化。顶部导航、各级菜单、内容容器、侧栏、底部区域及其选中／展开状态，默认都是保留项。

字段名、按钮、占位、Tooltip、辅助说明和错误提示沿准确来源使用。没有明确文案创作授权时，不自行润色、同义改名、补写业务概念或将库默认占位带回产品。

修改文本时还需保护分段字体、字号、颜色、链接、单位、空格和富文本样式；不能用整段赋值抹平不同片段。

### 4. 保留组件、变量与样式关系

- 优先使用所属库已有的组件、变体、属性和 Slots，核对真实母组件及嵌套关系。
- 规范库组件保留远程关联；业务自有本地组合母组件与必要依赖随副本完整复制。
- 不打散、删实例重画、静默换成近似组件，或用外置叠层冒充完整组件能力。
- 文本使用适用文本语义变量；颜色按用途、主题和解析后的真实值核对。
- 新增或修改自建布局的生效间距及 padding，包括 0，绑定适用现有间距变量并保留数值；无匹配时报告缺口，不凑档或造变量。
- 不擅自增删、重命名变量及集合，不因本地变量列表为空而认定远程绑定不存在。

### 5. 人民币金额补齐币种

本轮涉及的人民币金额统一带 `¥`，负金额写为 `-¥金额`，覆盖零金额、明细与汇总。该项是保留原型／旧稿内容的明确例外；原值、精度和分段样式不变，不重复添加已有符号，其他币种保留其币种。

### 6. 静态设计、原型与动效分别处理

默认交付静态设计，不新增演示连线；副本带入的演示交互和流程起点按目标范围清理，来源不动。用户明确要求可点击原型时才保留或新增相应连线。

涉及 Figma 动效时使用原生 Motion 时间轴与关键帧，并取得实际播放证据。静态页面、可点击原型、Motion 演示和真实业务运行结果分别说明。

### 7. 视觉偏好服从具体来源

没有更强来源时，可以使用大胆配色、明确字体节奏、有目的的颗粒、纸感、玻璃、光影、插画或动效。它们应服务信息和体验，不用于掩盖结构问题。

不默认套深色科技风或杂志风，不堆无依据的装饰卡片、渐变、徽章或发光；图标语言统一，不用 emoji 替代 UI 图标。详见 [taste.md](taste.md) 与 [去 AI 感检查](references/anti-slop-checks.md)。

## 完整执行流程

### 第一步：完整读需求，再读原型

读取正文、表格、规则、验收要求与有效修正，再检查关联 HTML 原型。正文嵌入附件和知识库子节点分别核实，不因子节点为空就判断没有原型。

识别新增、修改、删除和沿用项，确认适用端／版本／语言。记录字段、全部选项、默认值、条件、准确提示与必要展开态，区分业务逻辑变化和需要实际出稿的变化。

### 第二步：确认来源、目标和依赖

实时确认现行稿、页面、目标对象、主组件归属和实际样式，不凭文件名、记忆或静态清单猜测。

新需求按主规则中已确认的长期落点准备独立需求文件，先查重，再建立并置顶更新记录，启用所需库并确认可调用，随后复制必要业务稿和依赖。定点修改及定稿回迁按各自规则处理，不机械创建新文件。

建立受影响对象的来源对应关系，保存必要的修改前内容、结构、属性与渲染依据。复制整页后先核完整框架，副本已失真时先修复，不在错误底稿上批量派生。

### 第三步：按完整功能连续执行

以能独立查看和验收的功能为批次，连同相关弹窗及有依据的状态一起完成。创建时落实组件、变量、中文命名和容器规则，不先画一套临时错误稿。

批次是恢复单元，不是强制停工点。下一批与待检区域及共享依赖独立、写入结果已核实且没有会扩散的问题时，可以继续执行后集中交检。

### 第四步：合并检查内容、视觉与结构

对同一版最终稿进行集中核对：

1. 对照完整需求、原型及有效修正，检查应改内容是否落实。
2. 对照修改前依据和现行稿，检查保留项及页面框架是否受损。
3. 读回组件、变体、Slots、变量、富文本、自动布局和尺寸约束。
4. 查看完整页面及关键区域的本机渲染，核对齐、颜色、裁剪、投影和浮层。
5. 反查多画、误删、默认内容回流和没有来源的变化。
6. 集中修复明确问题，仅复查受影响内容及失效证据。

会扩大错误的目标错位、组件损坏或数据丢失即时处理，不等待批末。用户反馈可能存在同因时检查本轮适用范围，保留明确例外，不只修改被指出的单个位置。

### 第五步：记录、续做和交付

在任务工作区维护一份当前记录，包含有效来源、目标、范围、例外、批次、版本、已做／未做、检查状态、阻塞和下一步。

恢复后先核实实际结果。超时可能已部分写入，不能直接重跑整批或重复建文件、复制页面。技术故障不撤销已有授权，继续时沿有效记录补缺。

交付只声明有证据的范围，分别报告内容、视觉、结构、发布、实例同步和云端保存；未验证项单列。

## 表格与筛选专项规范

表格任务先确认行列模型，再选适用结构。普通明细、横向宽表、多层分组表头、跨行合并、单格多指标、多物理行指标、树形展开、多模块及连续报表可以组合，不能只按业务名称选模板。

### 当前明确的表格固定要求

| 要求 | 具体含义 | 不应误用的范围 |
|---|---|---|
| 每张表格额外展示一份完整表格 | 在所属画板下保留唯一一份不裁剪的完整展示，已有则复用；页内与完整展示同步修改 | 不另做末页展示，不伪造数据，不用完整表替代整页交付 |
| 序号列固定 52px | 逐行编号的序号／序列号列，表头、全部数据行与完整展示一致 | 业务单号等标识符不套用；没有序号列不自行新增 |
| 表格与分页外部间距为 0 | 末行或既定滚动视口底边紧贴完整分页组件，清除额外外部空隙 | 保留分页组件内部 padding，不靠负间距或手移坐标补救 |
| 分页直接使用完整库组件 | 通过已有属性、变体及 Slots 表达适用的总数、条数、页码和说明 | 不只取页码按钮，不手画或新建本地替代组件 |

### 结构、内容和统计口径

- 表头、数据行、合并格和汇总共享逐列宽度关系；分组父宽等于实际子列宽之和。
- 宽表区分页面视口与全列网格，保留完整列和固定边界，不把全部列压进窄视口。
- 跨行合并保留真实共享格与覆盖行高关系，不重复共享值后隐藏文字来模拟。
- 单格多指标、多个物理行和多个独立列按来源区分，不为复用方便改变业务模型。
- 当前页、全部筛选结果、去重统计、比率及父子小计分别核实，不能直接求和冒充全部汇总。
- 同格混排保留字体、颜色、单位、链接与换行分段；切变体后复核业务数据和覆盖是否保留。

### 对齐、筛选与长文本

金额、价格和数量列的表头与数据右对齐；标识符、联系方式、日期及复合指标格按语义和来源处理。文字、标签、按钮、图文及多行内容核格内垂直居中。

筛选 label 的准确文案、字数变体、容器宽度、对齐和控件间距分别核对。尾部说明及操作先占位，前部内容使用剩余宽度；不添加来源没有的查询／重置操作，也不从“没有查询按钮”推断所有控件立即生效。

长文件名和表格长文本通常一行省略，必要说明按语义换行。固定列、弹性列、滚动视口和内容高度各自按来源处理，不把所有容器改为 Hug，也不擅自隐藏列。

### 通用默认值与指定来源

报表细则还规定了无更具体来源时的模块间距、标题样式、明细／小计／总合计、增长率和占位表现。这些默认值与上述固定要求的适用边界不同，不能混为全局强制覆盖。

例如，汇总的标签、数字、增长率及点击能力分别配置，不因名称含“合计”就整行刷色；本轮人民币金额仍执行币种补齐例外。完整细则见 [表格设计规则](references/table-design-rules.md)、[创建执行方案](references/table-creation-workflow.md) 与 [筛选布局](references/tables-filters.md)。

## 组件库与动效专项规范

### 组件能力沿真实归属处理

通用样式、结构、状态和动效先追溯所属库母组件、嵌套和使用范围，在授权内修改对应能力。一次性业务内容可通过实例属性或受支持覆盖表达，不将实例数据写回所有消费者。

修改后分别检查母组件、相关变体和业务实例。发布由用户操作，未发布与未同步分开说明，不能由源库正确推断消费者已经更新。

### 属性必须真正生效

文案、显隐和插槽需真实绑定，不能以属性名称存在代替实际效果。新增状态或变体轴时保留原档外观和已有能力，不为凑矩阵制造视觉相同的状态。

新建图层、组件属性和变体值使用中文；已有库内部命名与必要专名保留，不为统一命名扩大修改范围。组件自身不自动增加用途说明、描述属性或说明画板，用户明确要求文档时再制作。

### 展示层同样需要验收

授权创建或整理组件规范展示时，组件内容、组名、弧形分组括号、行列标注和完整边界分别检查。适用的格子留白、Regular 标注及组间排布，见 [组件规范](references/component-spec-rules.md)，不据此重排无关组件集。

### 动效有独立验证条件

使用 Figma 原生 Motion 时间轴和关键帧，静态 UI 保持组件关联，由普通效果层承载适用运动。交付需区分已编辑时间轴、已实际播放及真实功能运行；一个视觉演示不能证明麦克风、网络状态或其他业务逻辑已经实现。

## 按复杂度组织协作

四个角色表示职责，实际启用方式取决于任务复杂度和当前宿主能力，不要求每个任务同时运行四个子 agent。

| 任务类型 | 执行方式 |
|---|---|
| 少量文案或局部样式修改 | 主 agent 完成核对、修改及一次针对性内容／视觉／结构检查，不额外交接 |
| 单端局部普通功能 | 主 agent 合并需求核对与设计执行，完成后一个检查子 agent 合并检查 |
| 多端、多版本、独立功能或共享库能力修改 | 按依赖和工具条件启用四类职责，复用适用角色实例并集中反馈 |
| 纯评审 | 由主 agent 或一个检查子 agent 合并只读检查，不启动复制和设计 |

| 角色 | 负责什么 | 写入边界 |
|---|---|---|
| Agent 1：需求核对与拆解 | 完整读需求，核原型与现行稿，确定实际变化、保留项和批次 | 不据拆解自行扩大出稿范围 |
| Agent 2：文件准备与设计执行 | 查重、更新记录、启用库、复用旧结构、完成设计及返修 | 只有当前承担设计执行职责者写入授权设计目标 |
| Agent 3：视觉与结构检查 | 对比来源与本机渲染，检查布局、样式、组件和变量 | 只读返回具体差异及证据 |
| Agent 4：需求与原型验收 | 正向核应有内容，反向核多画、漏项和误删 | 只读对照原始资料，不只信完成声明 |

所有角色继承相同的主规则、范围、来源和有效例外。共享 Figma 连接、页面或原生界面焦点时安排工具占用，不能边写同一区域边验收，也不能由检查者抢切执行目标。

若多 agent 不可用，按职责顺序执行并说明限制，不声称已完成独立复核。详细交接、返修和恢复方式见 [协作与轻量执行](references/multi-agent-workflow.md)。

## 验收与交付

验收同时检查“应该改变的已落实”和“必须保留的未受损”，并以同一版实际稿为依据。

| 维度 | 核验内容 | 主要证据 |
|---|---|---|
| 内容 | 范围、字段、顺序、选项、默认值、条件、完整提示、状态及金额 | 原始资料对照与实际内容读回 |
| 结构 | 主组件、嵌套、变体、属性、Slots、显隐、变量、主题、富文本及自动布局 | 当前节点和属性读回 |
| 视觉 | 对齐、间距、颜色、字体、图片、裁剪、投影、浮层、Section 和组件集展示 | 完整上下文与关键区域本机截图 |
| 边界与排布 | 可见后代、浮层、投影及完整展示的占用，画板与分区衔接 | 最终几何计算和渲染共同确认 |
| 保留与同因范围 | 未授权内容、独有信息、依赖、后续手改与明确例外 | 修改前后对照和适用范围复核 |
| 发布与同步 | 源库修改、用户发布、业务实例版本及云端保存 | 对应状态的独立证据 |

工具成功、实例存在、变量绑定非空、数量相同、截图存在或没有重叠，均不能单独证明整体通过。字体、换行、变体或尺寸再次变化后，受影响的几何与截图证据需要更新。

可使用的当前状态包括：待执行、执行中、已执行待验收、待返修、已验证、阻塞和不适用。尚未验证的内容不计入已完成范围。

最终交付说明实际改动、影响范围、验证结果和剩余缺口；纯评审只报告问题，已授权设计任务则在范围内完成明确修复与复核。

## 能力边界与常见问题

### 安装后会自动完成 Figma 编辑吗？

需要宿主选中或调用该技能，并具备对应工具和权限。规则文件不会自动安装连接服务、登录账号或授予编辑权限。工具不可用时，只能完成不依赖它的资料核对与说明，不能将计划描述为设计已落地。

### “按原型做”是否意味着把旧稿全部改成原型？

不意味着。需求与有效原型意图确定本次变化，现行稿仍提供保留内容和视觉基准。必须先辨别明确变更、沿用项和真实冲突，不能让原型省略或示意样式覆盖无关旧内容。

### 没有组件或变量时能否临时画一个？

先核实际所属库、远程绑定和现有依赖。仍缺失时说明具体能力缺口与影响，不能静默打散、伪造关联、造变量，或将自行拼装称为规范库复用；新增能力需按本轮授权边界处理。

### 是否会给每个任务补齐全部异常状态？

不会自动补齐。空、加载、失败、权限等也受状态来源限制，仅在旧稿、指定原型中有依据或获得用户明确新增指示时表达。

### 是否必须每批停下来审批？

来源、范围和授权已明确时直接推进，必要准备和既定验收不增加审批关。只有实际缺口、未决业务冲突、权限或范围变化影响执行时，才暂停依赖部分并提出具体问题。

### 评审发现问题后会直接改稿吗？

只读评审仅返回位置、差异、依据和影响。用户授权修改后，才按范围执行；若原任务已经授权设计与修复，则在该授权内处理明确问题。

### 本机验证通过是否代表已发布、已同步？

不能推断。库发布由用户操作，消费者实例版本和云端保存各需独立证据。静态设计也不能证明运行态键盘、读屏、网络或业务交互已经测试通过。

### 这是可直接生成前端代码的脚手架吗？

当前仓库以 UI/UX 设计规则、Figma 执行和检查流程为主，不附带前端脚手架、应用运行环境或一键还原程序。涉及代码实现时仍需单独确定技术栈、实现要求及验证环境。

## 规则维护

维护时先判断信息属于哪一类：

| 信息 | 放置位置 |
|---|---|
| 跨项目主流程、授权与共同约束 | `SKILL.md` |
| 已稳定的场景规则 | 对应 `references/` 文件 |
| 无更强来源时的个人视觉偏好 | `taste.md` |
| 用户明确保留、尚未稳定的通用想法 | `inbox.md` |
| 需求文案、业务方案、节点 ID、库 key、实测参数及进度 | 所属任务工作区 |

用户明确指定的长期工作区落点约定按主规则保留，一次性项目路由和文件清单不进入共享技能。局部画错先修本次，不自动升级为全局禁令。

收录时提炼对象、适用条件、执行动作、例外和验收方法，在原有对应规则中合并同义项并消除冲突。更新后核调用关系、相对链接、优先级和重复口径，并同步本说明中受影响的介绍。

静态校验可以确认名称、格式和引用，但不能证明真实设计任务效果已验证。实际有效性应以适用任务中的来源对照、读回和渲染证据为依据。
